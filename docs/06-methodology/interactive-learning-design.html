概述：这篇文档是什么，怎么用

这篇文档整理的是一套把"文档里的知识点"变成"可以动手玩的学习单元"的做法。 起因很直接：我们的知识库里已经沉淀了不少内容（比如 MySQL 知识地图）， 但纯文字读起来，机制类的知识（回表、MVCC、锁）总是"读的时候觉得懂了，过一阵又说不清"。 我们想把这类知识做成能单步执行、能改条件、能看结果变化的交互实验。做了一段时间后，把过程整理成这套流程，供以后每次加新知识点时照着走。

整套思路可以压缩成一句话：

原大纲决定知识覆盖，学习目标决定课程组织，知识机制决定交互形式，前置依赖和实现成本决定开发顺序。

展开就是下面这条流水线。后面每一节详细讲其中一步：

每一轮规划做完，手里应该留下三份东西（本文最后还会再总结一次）：

产出物回答什么问题什么时候更新
大纲映射表原大纲的每个知识点，用什么方式覆盖、关联哪个实验大纲增删改时
实验设计卡每个实验教什么、用户改什么、画面显示什么、怎么验证学会了实验开工前写，做完修订
分期实施表先做哪些、依赖哪些共用能力、每期验收什么每期结束时复盘调整

第一步：把学习目标写成一句能检验的话

规划一节课，最先写的不是内容大纲，而是学习目标。目标写不清楚，后面的画面、交互、练习都会跟着散。 我们把"学会"分成三个层次，一节课至少瞄准其中一个：

层次含义例子（索引主题）
解释能说清楚某个结果是怎么产生的能说出这条查询为什么走了回表
预测改一个条件后，能判断结果会怎么变把 SELECT 的字段换掉，能预测还会不会回表
应用换个场景，能自己做选择并说明理由给一张新表设计索引，并解释为什么这样建

写目标的句式固定成这样，写完自己检查能不能被验证：

学完这一节，用户能够在「某个场景」下，判断或完成「某件事情」，并用「某种证据」解释原因。

拿两个例子对比一下，差别就很清楚：

  • 不合格："理解事务"、"掌握索引"——没法检验，也没法据此决定画面里该出现什么。
  • 合格："给定两个事务的操作顺序，能够预测某次查询会读到什么，并说明判断依据（读到的是哪个版本、为什么是它）。"

目标写具体的好处是：它会一路约束后面的决定。比如上面这个事务目标，画面里就必须出现"两个事务的时间线"和"行的版本"， 练习就必须让学习者先预测再揭晓，而不是做成一个可以随便点的玩具。

第二步：认清三种结构，别混在一起

做课程时其实同时存在三种"结构"，它们各有各的职责。混在一起想，很容易乱；分开管，事情就清楚了：

结构回答的问题怎么组织
知识结构MySQL 包含哪些知识，彼此什么关系？以原大纲为准，保留章节、层级和编号（如 MySQL 知识地图）
教学结构用户按什么顺序学，在哪个实验里理解？按前置知识、学习问题、理解难度组合成教学单元
开发结构先做哪些，哪些能力可以复用？按教学价值、依赖关系、内容准确性、实现成本排期

三种结构之间有一个必须记住的关系：知识点和学习活动是多对多。

  • 一个知识点可以有多个学习活动：比如"回表"既可以在索引实验里观察，也可以在执行计划练习里判读。
  • 一个实验也可以覆盖多个知识点：比如"改索引列、观察查询路径"一个实验，就同时牵到索引结构、主键、二级索引、覆盖查询四个知识点。

所以每张设计卡都要写"对应大纲节点"（可以多个），每个大纲节点都要标注"通过什么方式覆盖"。两边都能查得到，才算把账记清了。覆盖方式用固定几个词，别发明新说法：

覆盖状态含义
独立课程覆盖专门为它做了一个（组）实验或课程
作为前置说明不单独成课，在别的实验开头铺垫
参考内容覆盖一张对比表或一篇参考条目就够
后续阶段展开值得做，但这期不做，位置先留着
建议补充做实验时发现大纲缺了必要的前置知识，单独标出来待定
待澄清还没想清楚怎么覆盖

第三步：动手前，先回答六个问题

这是整套方法里最要紧的一节。每个知识点转成课程之前，都把这六个问题过一遍。 答不上来的，先别开工——多半是还没想清楚要教什么。

问题一：用户学完后，具体要会什么？

把"理解""掌握"这类词，换成一个能观察到的行为。写的时候就套上一节那个句式。 例子：把"掌握事务隔离级别"改成"给定两个事务交错的操作顺序，能预测某次查询读到什么，并说明是哪条可见性规则决定的"。 前者没法检验，后者可以直接出一道题来检验。

问题二：用户最容易在哪里理解错？

先想清楚值得解决的理解障碍，再决定课程的轻重缓急。误解从哪来？三个渠道最有效：自己的学习经历、工作里踩过的坑、以及真实学习者提问时卡住的地方。 比如这几个就是我们记下来的高频误解：

  • "覆盖索引是一种索引"——其实它只是"这次查询需要的列都在索引里，所以不用回表"这种状态。
  • "SELECT 都是读快照"——SELECT ... FOR UPDATE 是当前读，读的是最新版本。
  • "加了索引就一定快"——联合索引的条件顺序写错、字段上套函数，都可能用不上。

哪些地方要慢下来讲、哪些地方值得专门做个对照实验，就看这张误解清单。

问题三：哪个最小场景能把问题展示清楚？

场景越小，注意力越能放在关键机制上。目标是找到刚好够用的数据量和参与方：

  • 索引课可能只需要一张 10 行的小表：users(id, name, age, city) 加一个二级索引。
  • 并发课只需要两个事务（事务 A、事务 B），不需要"高并发"的场面。
  • 能不引入的概念就不引入：讲回表时先不做索引下推，等下一个实验再加。

问题四：用户可以改变什么？

交互要跟学习目标直接挂钩，不是"哪里能点就点哪里"。常见的可改变量就这几类：

  • 查询返回哪些字段；
  • 索引包含哪些列、列的顺序；
  • 数据分布（某列的重复度高低）；
  • 两个事务谁先执行、下一步轮到谁；
  • 提交（或崩溃）发生的时机。

每一轮只改一个变量。一次改两个，就算结果变了，学习者也说不清是哪个引起的——实验就白做了。

问题五：改变之后，用户能看到什么证据？

改了条件，画面必须给出能指着说的变化。合格的标准是学习者能说出这句话： "因为这里变了，所以结果变了。"常见的证据有：访问路径（走了哪个索引、停在哪里）、行的版本（读到的是哪个）、 锁的持有与等待关系、执行计划里的行数估算、日志的先后顺序。

反过来，如果一个知识点"改了什么画面都不怎么变"，那它多半不适合做成实验——一张图或一张表就讲透了，别硬做。 问题四（能改什么）加问题五（改了看什么）合在一起，就是"值不值得交互化"的判断标准。

问题六：怎么判断用户已经理解？

最后给一个稍有变化的新场景，让学习者自己预测、解释或操作一次。这个环节可以很小， 但它检验的是"刚才的机制能不能搬到新问题上"，也就是我们最看重的"迁移"。比如刚做完"返回 name 不回表"的实验， 迁移挑战就出"现在返回 age，会回表吗？为什么？"

六个问题放在一起，方便随时对照：

#问题一句话要点
1学完具体会什么？写成能观察、能检验的行为
2最容易在哪理解错？误解清单决定轻重缓急
3最小场景是什么？数据越少越好，概念能省则省
4用户能改变什么？每轮只改一个变量
5改了能看到什么？要能指着画面说"因为这里变了"
6怎么验证已理解？换个小场景，做一次迁移

不是所有知识都适合做实验。判断标准很简单：哪种形式最能帮用户理解，就用哪种。下面这张表是我们实践下来最常用的对应关系， 最右一列放了 MySQL 里的例子，方便对号入座：

组成关系、层级、数据结构结构图、可展开的图、对象检查看清组成、位置和关系 表空间→段→区→页→行；B+ Tree 结构

同一个主题里，不同知识点的形式可以完全不同。比如索引这一章：B+ Tree 画一张结构图就够讲清楚； "回表还是覆盖"就值得做一个改量对比实验；"主键怎么选"更适合给两个方案做比较。 课程做没做够，看的是知识覆盖和学习效果，不是实验数量。一个知识点用一张好图讲透，比硬凑三个实验强。

第五步：机制类课程的固定节奏

对"有机制、能观察"的课程（事务、锁、索引这类），我们统一用五个步骤推进。固定节奏的好处是：学习者熟悉一次流程后， 以后每节课都能把注意力放在知识本身，不用重新学"怎么用这个页面"：

  1. 提出问题：用一个具体场景说清这节课要解决什么。
  2. 先预测：动手前让用户说出自己的判断。猜错比猜对学到的多。
  3. 单步观察：一步一停，检查当前的对象和状态。
  4. 改一个变量对比：只改一个条件，重新跑一遍，和上一轮对比。
  5. 迁移挑战：换个小场景，要求独立解释或操作。

拿"回表与覆盖索引"这一节把节奏走一遍，每一步长什么样就清楚了：

步骤具体做什么
1 提出问题"同样查 10 个用户的姓名，为什么这条快、那条慢？"给出两张小表和两条 SQL
2 先预测让用户点选："这两条查询，哪条需要回到主键索引取数据？"先存答案，不急着揭晓
3 单步观察逐条高亮：先看二级索引里有哪些列 → 再看查询要哪些列 → 最后看查找停在了哪里
4 改量对比把 SELECT 的 name 改成 age，重跑；画面并排显示两轮的访问路径差异
5 迁移挑战给一条新查询："SELECT city FROM users WHERE name='x'"，预测是否回表并解释

对应到页面上，每一节课都围绕五个区域组织：当前任务、可操作的条件、核心画面、步骤解释、挑战反馈。另外，每节课要指定一个主要的观察层次，避免画面里什么都看等于什么都没看：

课程主要观察什么
索引索引记录和行数据
事务 / MVCC操作时间线和数据版本
锁锁的持有、请求和等待关系
执行计划操作节点及其处理的数据量
日志与恢复日志写入顺序和落盘时机

每个实验开工前，先填一张固定字段的设计卡。所有实验用同一套字段，好处是完整度可以直接对比，交接给设计和开发时也不用反复解释。 字段如下：

字段填什么
对应大纲节点原大纲的章节与编号，可以多个

实验问题一句话，学习者进来看到的那个问题

可修改变量用户能改什么；注明每轮重点改哪一项
主要观察对象画面里盯着看的那几个对象
可见证据改完之后，画面上具体发生什么变化
迁移挑战换个什么新场景，要求预测或解释什么
适用范围与假设版本、引擎、并发条件、省略了哪些细节
验证方式怎么确认模型教的和真实行为一致

第六步：从零散实验到一条学习路线

设计卡有了之后，按四步把它们组织成一条能学下去的路线。

8.1 先做完整的大纲映射

对着原大纲（保留原有章节、层级、编号），给每个节点补六项：学习目标、前置知识、主要理解障碍、建议呈现形式、关联实验、覆盖状态。 覆盖状态就用前面那几个词。这一步做完，哪些做了、哪些暂缓、哪些没想清楚，一目了然。 做实验时发现缺前置知识的，单独标"建议补充"，再决定要不要加进大纲。

8.2 组合成教学单元

把适合一起理解的知识点组合成"教学单元"，每个单元写清四件事：进来之前要会什么、这次集中解决什么问题、做完获得什么能力、后面能接到哪些课。 以我们的 MySQL 规划为例，大致是这样一条线（详细规划另见规划文档）：

单元集中解决前置
U1 一条 SQL 的旅程语句怎么被执行、执行计划怎么读无
U2 索引实验室索引记录与行数据的访问路径U1
U3 事务与 MVCC 实验室两个事务交错时各自"看见什么"U1
U4 锁与死锁实验室谁持有、谁等待、为什么死锁U3
U5 日志与崩溃恢复不丢数据的代价、恢复时怎么判定U3、U4 概念
U6 复制与高可用延迟在哪一段、一致性代价U5
U7 查询优化工作台优化器决策与 SQL 改写U1、U2
U8 设计与运维设计取舍与操作流程前面各单元

8.3 选第一批做什么

第一批内容按这几条标准挑：

  • 有明确的理解障碍，交互确实能帮上忙；
  • 前置知识清楚，范围控制得住；
  • 机制能准确建模，行为能被验证；
  • 能形成"问题 → 实验 → 挑战反馈"的完整体验，而不是半截演示；
  • 用到的画面、数据、交互能力，后面的课还能接着用。

实际选择时还有一个现实条件：前置内容是否已经成文。比如我们把"索引实验室"排进第一批， 很大一部分原因是它依赖的分层架构与执行计划两篇文档已经写完（见 分层架构、 SQL 层与执行计划）， 范围可控、误解集中，适合打样。

8.4 反推要开发的共用能力

把设计卡排在一起看，会发现很多实验需要同样的底层能力。先做这些"零件"，后面的课就是搭积木，而不是每次都从头写：

共用能力说明哪些课要用
单步执行 + 状态回退一步一步跑，能退回上一步重看几乎全部机制课
对象检查器点击对象展开内部字段（页结构、行版本、锁）U2、U3、U4
条件切换与对比改一个条件重跑，两轮结果并排比较U2、U3、U5、U7
双事务调度两个事务轮流推进，时间线上显示交错U3、U4
执行计划渲染把计划画成节点树，标出每个节点的数据量U1、U7
预测与挑战判分先存预测再揭晓，能对"解释"给反馈全部实验的第 2、5 步
场景数据脚本用数据描述表结构、初始数据、步骤序列、标注全部
边界标注组件版本、引擎、简化假设的统一角标全部

分期实施表示例（摘要）：

阶段内容验收（验理解，不只验画面）
P0 基座设计卡模板、场景数据格式、边界标注、单步引擎雏形一个无交互的单步演示能跑通
P1 索引实验室E1 查找路径、E2 回表与覆盖、E3 联合索引与索引下推能完成迁移挑战并给出正确解释
P2 事务与锁隔离级别交错、版本链与 Read View、加锁范围、死锁能预测交错顺序的读结果、画出锁的持有与等待
P3 日志与恢复flush 参数对照、两阶段提交、崩溃点推演能推演某个崩溃点对应的恢复结局
P4 复制与优化复制流水线、延迟归因、SQL 改写对照能归因延迟、解释改写的收益

几条不能丢的约束

这几条直接影响课程可不可信、好不好维护，任何时候都不要省：

  1. 模型的边界要写清楚。每节课标注版本、存储引擎、初始状态、简化假设。 还要区分"教学步骤"和"实测耗时"——演示里的一步是一拍，不代表真实执行就是这个速度。这和本仓库"版本标注、不编造"的要求是一回事。
  2. 每次交互都要有看得懂的状态变化。学习者要能回答三个问题：我改了什么？哪个对象发生了变化？这个变化意味着什么？ 答不上来就是无效交互。
  3. 教学"上一步"和 SQL 的 ROLLBACK 分清楚。前者是页面上的回看功能，后者是实验内容里的真实操作。 两者的表达（文案、图标、说明）必须区分开，不然学习者会把"退回看看"理解成"数据库回滚了"。
  4. 验收要看理解过程。除了检查画面和操作正常，还要看学习者能不能解释结果、预测变化、完成新场景。 画面再漂亮，学完说不出所以然，就退回设计阶段找原因。
  5. 每个模型都要有验证方式。教学模型讲的，必须能用真实环境核对（EXPLAIN、EXPLAIN ANALYZE、官方文档）， 核对方式写在设计卡里。这保证我们"教的"和"真实发生的"一致，符合仓库"来源可溯"的红线。

参考案例：Protocol Explorer

Protocol Explorer 是一个把互联网协议做成交互模拟的教学站， 原作者 Dilum Sanjaya。它和我们要做的事高度相似（也是"把抽象机制变成可观察的过程"）， 实际体验过之后，值得借鉴的点整理如下。想看完整分析可以看我们的规划讨论记录，这里只留结论。

它做得好的地方：

  • 每个协议是一条固定步数的旅程（比如 HTTP：客户端请求 → DNS 解析 → TCP 连接 → HTTP 交换 → 页面渲染），步骤就是目录，也是进度。
  • 统一的"观察台"布局：左边知识目录，中间主画布（拓扑图和时序图可一键切换），右边对象的元信息卡，下面 Wireshark 风格的数据包流水表 + 播放 / 单步 / 上一步 / 重置控件。
  • 字节级检查器：点开任何一个数据包，能看到分层的头部解码，每个字段配一句教学注释，旁边还有十六进制原始视图。
  • 真实感和诚实并存：数据像真实抓包，但到处标注"示例值，每次真实抓包都不一样""未显示数据的 ACK""加密的字节无法展示"——把简化假设写在了界面上。
  • 故障对照场景（丢包、重传、队头阻塞 vs QUIC），正好是"改一个条件看后果"的示范。
  • 纯静态站点，双击就能离线跑，GitHub Pages 就能发布；场景由声明式数据驱动（一段数据描述包序列和标注）。

可以直接借到我们项目里的：

它的机制对应我们的
协议旅程（分步叙事）U1"一条 SQL 的旅程"的阶段叙事
拓扑 ⇄ 时序双视图双事务时间线（U3/U4）、复制流水线时序（U6）
数据包流水表实验记录表：访问路径、锁等待、LSN 流水
字节级检查器 + 字段注释对象检查器：页结构、行版本、Read View 字段
"示例值 / 未显示 / 不可展示"标注边界标注组件（对应本文第 9 节第 1 条）
播放 / 单步 / 上一步 / 重置控件单步执行 + 状态回退的交互语义
模块进度跟踪分期实施表的完成度展示

它没做、我们要补的（也是从"演示"到"学会"的关键差距）：

  • 没有"先预测再揭晓"的环节，也没有迁移挑战——看懂就结束了；
  • 场景是固定的，没有"改一个变量重跑"的对照实验；
  • 不需要大纲双向追溯和版本标注（我们标 MySQL 版本、引擎、隔离级别，它标 RFC）。

顺带一提：它证明了"浏览器内教学模型 + 明示简化假设"这条技术路线可行、成本可控， 不必强求连真实数据库跑实验。真实实例放在每张设计卡的"验证方式"里做核对即可。 许可方面，该项目为 MIT 协议：借鉴交互模式没有问题；如果直接复用它的代码，需保留原作者的版权声明和许可文本。

最后：三份产出物怎么用

每轮规划收尾时，对着这三份东西检查一遍：

产出物自检问题
大纲映射表有没有知识点是"待澄清"却没人跟进？新加的实验能回溯到大纲编号吗？
实验设计卡可修改变量和可见证据都写清楚了吗？验证方式填了吗？
分期实施表这期的验收标准是"能解释、能预测"，还是只写了"页面可用"？

方法本身也是在实践里长出来的，遇到这套流程不适用的地方，就回头改流程、更新这篇文档。 有一点建议从第一个实验就坚持：宁可场景小一点、内容少一点，也要让每个实验走完"问题 → 预测 → 观察 → 对比 → 迁移"的完整闭环。 一个走完全程的小实验，比三个只能看的动画有用得多。
