适用：Redis Open Source 7.2.x；单机、主从复制、Sentinel 和原生 Cluster。文中另行标注跨版本差异。

1. 总览：一条写命令的旅程

把 Redis 理解成一台按命令操作内存数据结构的服务器。用 SET demo:session active EX 60 串起它的机制：客户端找到目标节点，主线程写入 String 并设定 60 秒有效期。此后，多久能读到、重启能否恢复、切主后能否读到，分别由内存中的 key 生命周期、持久化配置、复制与故障转移决定。对这条命令收到 OK，只能据此确认目标节点执行成功；磁盘与副本的进度需要另外判断。

2. 数据模型：按访问方式选类型

key 是二进制安全的字符串，value 有类型。HGET 等类型专用命令要求 value 类型匹配，TTL 等通用命令不受类型限制。冒号分隔的前缀只是命名约定；逻辑数据库也不提供独立的内存配额。Cluster 只支持 DB 0。

类型表达什么典型用法代价要看什么
String字节串，可表示整数GET / SET 做缓存；INCR 做计数大 value 即使只查一个 key，也会增加网络传输和客户端处理时间。
Hash字段到值的映射HGET / HSET 读写对象字段HGETALL 要读取整个 Hash，开销随字段数增长。
List保序、允许重复的序列LPUSH / RPOP 从两端处理任务弹出即移除；如果消费者崩溃，需要额外设计确认和恢复。
Set无序、去重的成员集合SISMEMBER 查成员；SINTER 求交集集合运算要看参与集合的大小，返回量也可能很大。
Sorted Set成员唯一，按 score 排序ZADD / ZRANGE 做排行榜限定范围和返回量，避免频繁拉取整榜。
Stream带 ID 的消息日志XADD 追加；XREADGROUP 消费；XACK 确认设置保留策略，处理未确认消息与重复投递；消费者应能幂等处理。

Bitmap、HyperLogLog、Geo 分别适合位标记、近似去重计数和地理范围查询。TYPE 看逻辑类型，OBJECT ENCODING 看当前内部编码。例如，小 Hash 可用紧凑的 listpack；超过相应大小限制后可能转成哈希表。估容量时应测代表性数据的实际内存，不能只把 value 的字节数相加。

消息机制：Pub/Sub 把消息送给在线订阅者，最多投递一次，断线后无法补读；Stream 在记录仍保留时可以按 ID 补读，消费组跟踪已投递但未确认的消息。XACK 更新消费组的确认状态，不删除消息本身；重启或切主后的可恢复性仍取决于持久化和复制。

3. 执行：事件循环、批量请求与原子性

单个 Redis 7.2 节点用事件循环和 I/O 多路复用处理多个连接，数据命令主要由主线程串行执行。io-threads 默认是 1；设得更高可把部分 socket 写交给 I/O 线程，另开 io-threads-do-reads yes（默认关闭）可让它们处理读入和协议解析。网络 I/O 成为瓶颈时才考虑这两个设置，并先压测 CPU 和尾延迟；Redis 7.2 的线程化 I/O 不支持 TLS，也不会并行执行数据命令。慢命令或长脚本占住主线程，其他连接也要等。

需求机制保证与边界
减少网络往返Pipeline连续发送一批命令，再读取回复。命令仍分别执行，没有事务隔离；批次太大时服务端要缓存更多回复。
一组命令执行期间不被插队MULTI / EXEC先入队，再连续执行。入队阶段出错可使整批不执行；执行阶段某条命令出错，其他命令仍会执行，已完成的修改也不会回滚。
读取后仅在数据未变时写入WATCH + 事务乐观并发控制：在 EXEC 前，监视的 key 被修改（包括过期或淘汰）就放弃本次事务；客户端按业务需要重试。
在服务端完成依赖前一步结果的判断与更新Lua（EVAL）或 Redis Functions（7.0 起）执行过程中其他命令不插入。脚本要限制循环和数据规模；中途报错不会撤销已经完成的写入。

4. 内存：过期、淘汰和实际占用

过期由时间触发。在 Redis 7.2，TTL 设在整个 key 上；Hash 字段级过期 HEXPIRE 从 7.4 开始支持。主节点访问到过期 key 时会按不存在处理并触发清理，也会主动抽样清理没有被访问的过期 key。到期和内存实际释放可能不在同一时刻。TTL 返回剩余秒数，-1 表示存在但无过期时间，-2 表示 key 不存在。普通 SET 覆盖会移除旧 TTL，除非重新指定过期时间或使用 KEEPTTL。

淘汰由内存压力触发。64 位 Redis 7.2 中 maxmemory 默认 0，即不设这一限制；设置上限后，默认 noeviction 会在内存不足时拒绝需要额外内存的写入。允许淘汰时，allkeys-* 可从所有 key 中选，volatile-* 只从设有 TTL 的 key 中选，后者没有候选时也会拒绝这类写入。LRU 近似按最近访问时间选，LFU 近似按访问频率选，volatile-ttl 优先淘汰剩余有效期较短的 key。只有业务允许 key 提前消失时才适合启用淘汰。

容量要看字节和趋势。maxmemory 是淘汰判断的上限，不能当作进程 RSS 或容器内存上限。对同一节点比较 used_memory 与 used_memory_rss，记录差值（字节）及趋势；差值大时再用 allocator_frag_bytes 判断是否主要来自分配器碎片。设置 maxmemory 时还要为复制/AOF 缓冲（mem_not_counted_for_evict）和快照/重写期间的写时复制留空间，最终与主机或容器的内存限制核对。

5. 持久化：进程重启能恢复到哪里

机制启用条件写入与恢复代价和丢失窗口
RDBsave 自动快照条件满足，或显式触发快照后台快照保存某一时点的内存数据；恢复时加载快照。只能恢复到最近一次可用快照所记录的时点。save "" 禁用定时快照；不影响手动快照或复制时生成的快照。
AOFappendonly yes（默认 no）记录数据变更，启动时重放。7.0 起由基础文件、增量文件和 manifest 组成；重写生成新的基础文件以压缩历史。本地丢失窗口取决于 appendfsync、磁盘状态和故障方式；还要承担写入与重写的资源开销。

Redis 7.2 默认 save 3600 1 300 100 60 10000；每对值是「距上次保存的秒数、至少发生的变更数」，满足任一组就可触发后台快照。提高快照频率可缩小恢复窗口，但会增加后台操作。appendfsync 默认 everysec，通常约每秒刷盘，异常掉电时约一秒的数据可能丢失，这不是严格上界。always 更频繁地刷盘，适用于能接受较高写延迟、希望缩小丢失窗口的场景；no 交给操作系统决定刷盘时机，丢失窗口更难预估。

后台 RDB 快照和 AOF 重写仍有 fork 暂停、写时复制与磁盘 I/O 开销，写入越密集越需要关注峰值。两者都启用时，正常启动优先用 AOF 恢复。需要从误删或整机损坏中恢复时，还要保留独立备份并演练恢复。

6. 复制、Sentinel 和 Cluster：节点故障后由谁服务

Redis 默认异步复制。主节点把变更送入复制流；副本断线重连后通过 PSYNC 提交复制 ID 和偏移，主节点仍认可这段历史且 backlog 覆盖缺口时可增量续传，否则要用 RDB 快照和后续变更做全量同步。副本可能读到旧值，故障转移也可能丢失主节点已确认、但新主节点未收到的写入。WAIT 等待同一连接先前写入的复制确认，应检查返回的副本数量；确认不代表已刷盘，也不提供强一致。7.2 起，启用 AOF 时可用 WAITAOF 等待指定的 AOF 刷盘确认，也要检查返回结果。

部署数据如何组织主节点故障时
单机全部数据由一个节点服务等该节点恢复，能恢复多少取决于持久化或上游数据源。
主从复制一份数据，有一个或多个副本只配复制没有自动切主，需外部系统或人工切换。
Sentinel监控主从复制组，不切分 keyspaceSentinel 确认主节点故障，选举后提升副本；客户端通过 Sentinel 发现新主。
Cluster多个主节点分别管理一组 slot满足选举和副本条件时，故障分片的副本可接管其 slot，客户端刷新路由。

Sentinel 的两个门槛：quorum 是判定主节点客观下线所需的同意数；授权执行自动故障转移还需至少获得 Sentinel 的多数票，且不得少于 quorum。这两个门槛分别回答「是否判定故障」与「能否开始切换」。

Cluster 的路由：key 经 CRC16 映射到 16,384 个 slot 之一，再由 slot 找到主节点。原生多 key 命令所涉及的 key 要在同一 slot，可用 hash tag（例如 order:{42}:meta 和 order:{42}:items）显式聚到一起；集中使用同一个 tag 容易造成分片负载倾斜。CROSSSLOT 表示请求涉及不同的 slot，即使它们碰巧归同一个节点也不能直接执行。MOVED 提示客户端更新路由；迁槽期间的 ASK 只为当前请求临时重定向，目标节点先接收 ASKING。

7. 排查：从现象找到对应机制

先确定请求实际落在哪个数据节点。Cluster 的 INFO、SLOWLOG、SCAN 都是节点视角；复制问题要对照主节点和对应副本。下表命令均在 redis-cli 连接到指定节点后执行。

现象先看什么怎么判断
key 提前读不到TTL demo:session；INFO stats对比同一时间窗口内 expired_keys、evicted_keys 的增量，区分实例是否发生过期或淘汰。TTL=-2 只能证明当前不存在，不能定位该 key 消失的原因。
写入报 OOM 或 RSS 上涨INFO memory；INFO stats核对 maxmemory、maxmemory_policy、evicted_keys 及 RSS 与分配器指标；把拒绝写入与主机内存压力分开判断。
客户端延迟升高SLOWLOG GET 10；INFO commandstats；INFO stats把客户端 P99 与慢命令和 instantaneous_ops_per_sec 的变化对齐。SLOWLOG 记录命令实际执行时间，不包含网络、排队等时间；没有慢日志也要看连接池、排队、网络和 fork。
重启后缺数据或重启变慢INFO persistence；启动日志、实例配置、磁盘指标用日志核对启动加载的文件，用 INFO 看快照和重写状态，再对照实际 save、appendonly、appendfsync 配置和磁盘耗时。
副本读旧值或切主后缺数据主节点和副本的 INFO replication检查副本的 master_link_status 以及同一复制历史下的偏移差；偏移差以字节计，不能直接换算成延迟秒数。
Cluster 反复重定向CLUSTER INFO；CLUSTER SHARDS（7.0 起）检查集群状态，把 slot 当前归属与客户端缓存的路由对照，再检查是否正在迁槽或刚切主。

排查大 key 与热 key：用 redis-cli --bigkeys 按类型找出元素多或值长的 key，再用 MEMORY USAGE demo:session 估算候选 key 的字节数。按前缀查找可在 redis-cli 会话中从 SCAN 0 MATCH demo:* COUNT 100 开始，按返回游标继续，直到游标返回 0。结果可能重复，COUNT 只是提示。热 key 优先从客户端按 key 采样；已使用 LFU 淘汰策略的节点可用 redis-cli --hotkeys 做抽样。指定目标实例的主机和端口；Cluster 按目标分片逐节点执行。全量扫描仍会消耗 CPU 和网络，线上应低峰限速。分享慢日志或扫描结果前先脱敏。

8. 在测试实例观察 TTL 与事务

在本机隔离的 Redis 7.2 测试单机（默认端口 6379、DB 0）运行 redis-cli，在同一会话依次输入。使用专用演示 key demo:session。

SET demo:session active EX 60
TTL demo:session
SET demo:session renewed
TTL demo:session
EXPIRE demo:session 1
TTL demo:session

第一条 TTL 看剩余秒数；第二条应为 -1，说明覆盖值时丢掉了旧 TTL。执行 EXPIRE 后等超过 1 秒再输入最后一条 TTL，预期为 -2。这个实验只需要观察 key 生命周期，不依赖磁盘或副本设置。

再用同一个测试实例验证运行期错误：以下命令要在同一个 redis-cli 会话执行。LPUSH 对 String 操作会报 WRONGTYPE，前后的 SET 仍然生效。

MULTI
SET demo:txn first
LPUSH demo:txn item
SET demo:after yes
EXEC
GET demo:txn
GET demo:after

个人实验验证：TTL 的返回语义、覆盖移除 TTL 及事务运行期错误行为，均在隔离的 Redis 7.2.17 单机验证，RDB 和 AOF 均关闭。
