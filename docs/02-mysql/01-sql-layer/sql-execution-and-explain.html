适用：MySQL 8.0.x（与 5.7 的差异单独标注）。知识地图见 MySQL 知识总览，上一章 MySQL 总览：一条 SQL 的旅程。

目标：说清一条 SQL 在 Server 层经历的四个阶段，理解优化器「为什么这样选」，并能熟练读懂执行计划。

1. 本章全景

阶段回答的问题典型报错
解析这句话符合语法吗1064 You have an error in your SQL syntax
预处理表和列存在吗，有权限吗1146 Table doesn't exist、1054 Unknown column、1052 Column ambiguous
优化用什么办法执行最省无报错，但可能「选错索引」导致慢
执行按方案取数、过滤、返回运行期错误（超时、数据截断、除零等）

2. 解析器

2.1 做什么

  • 词法分析：把字符串切成 token，识别关键字、标识符、字面量、运算符。
  • 语法分析：按 MySQL 语法规则（基于 bison 生成）把 token 组装成语法树（AST / parse tree），语法不合法在这里直接报 1064。

2.2 要留意的点

点说明
保留字用保留字做表名 / 列名需要加反引号。8.0 新增了保留字（如 RANK、GROUPS、WINDOW、LATERAL 等），从 5.7 升级时旧 SQL 可能突然报语法错
sql_mode影响解析行为，如 ANSI_QUOTES（双引号变标识符）、PIPES_AS_CONCAT（|| 变字符串连接）
预编译语句PREPARE / EXECUTE（驱动里的 server-side prepared statement）只解析一次，后续只传参数；同时是防 SQL 注入的主要手段。注意 MySQL 没有跨语句的执行计划缓存，每次执行仍会重新优化
报错位置报错信息里 near '...' 指出的是解析器卡住的位置，真正的错误往往在它前面一点

3. 预处理（Resolve / Prepare）

语法正确后，Server 要把语法树「绑定」到真实对象上：

  1. 名字解析：表、列、别名是否存在、是否有歧义；SELECT * 展开成具体列；视图展开成底层查询。
  2. 权限检查：对表 / 列的权限（连接阶段只做了认证和全局权限）。
  3. 打开表并加元数据锁（MDL）：这也是 DDL 和长事务互相阻塞的根源，详见锁章节。
  4. 语义检查与类型推导：确定每个表达式的类型，决定哪里会发生隐式类型转换（这是「索引失效」的常见来源之一）。
  5. 部分逻辑改写：如子查询转换为半连接（semijoin）、视图 / 派生表合并。这部分与优化器的逻辑优化衔接紧密，不同版本归属略有差异，理解为「正式选计划前的等价改写」即可。

4. 优化器

优化器的任务：在语义等价的前提下，找到成本最低的执行计划。分两层：

4.1 逻辑优化（等价改写）

改写示例 / 说明
常量折叠与传播WHERE a = 1 + 2 → a = 3；a = b AND b = 5 → a = 5 AND b = 5
无用条件消除WHERE 1=1、恒假条件直接得到 Impossible WHERE
外连接转内连接LEFT JOIN 后 WHERE 中对右表有非空条件，则等价于 INNER JOIN，从而获得更多 join 顺序可选
子查询优化IN / EXISTS 子查询转 semijoin（策略：FirstMatch、LooseScan、Materialization、DuplicateWeedout）；不能转换时物化（Materialization）或按相关子查询执行
视图 / 派生表合并derived_merge：把派生表直接合并进外层查询，避免物化；8.0.22+ 还支持把条件下推到物化的派生表里
分区裁剪根据条件排除无关分区

4.2 物理优化（基于成本，CBO）

核心是枚举候选方案并估算成本，选最小的。要决定三件事：

  1. 每个表怎么访问：全表扫描、索引扫描、索引范围扫描、索引等值查找、index merge……
  2. 多表 join 的顺序：n 个表有 n! 种顺序，MySQL 用贪心 + 剪枝（optimizer_search_depth、optimizer_prune_level）控制搜索量，表很多时优化本身也有开销。
  3. join 算法：Nested Loop、Hash Join（8.0.18+）、BKA 等（详见查询优化章）。

成本模型

  • 总成本 ≈ IO 成本 + CPU 成本。IO 按读页数估，CPU 按处理行数、比较次数、临时表代价等估。
  • 单位成本常量存在系统表 mysql.server_cost 和 mysql.engine_cost，可以调整（生产上一般不动）。
  • EXPLAIN FORMAT=JSON 的 cost_info 里能看到 query_cost、read_cost、eval_cost、prefix_cost。

4.3 统计信息（优化器的「眼睛」）

优化器看不到数据，只能靠统计信息估算，估算偏差是选错计划的头号原因。

统计来源说明
表统计行数、数据页数，存于 mysql.innodb_table_stats
索引统计每个索引的基数（Cardinality，不同值个数的估计），存于 mysql.innodb_index_stats；SHOW INDEX FROM t 可见
采样方式持久化统计（innodb_stats_persistent=ON，默认）按随机采样若干页估算，采样页数 innodb_stats_persistent_sample_pages（默认 20）
更新时机表中约 10% 行变动后自动重算（innodb_stats_auto_recalc）；也可手动 ANALYZE TABLE t
直方图（8.0）针对没有索引的列记录值分布：ANALYZE TABLE t UPDATE HISTOGRAM ON col WITH 100 BUCKETS;，数据在 information_schema.COLUMN_STATISTICS。不会自动更新，数据分布变了要手动重建
索引潜水（index dive）对 range / IN 条件，优化器直接去索引树里数匹配行数，比统计更准；但 IN 值个数超过 eq_range_index_dive_limit（默认 200）后退化为用索引统计，估算变粗

4.4 优化器为什么会「选错索引」

原因说明
统计信息不准采样偏差、数据分布倾斜、统计过期
回表成本被低估 / 高估二级索引命中行数多时，回表是大量随机 IO；经验上命中比例较高（量级上到总行数的两三成）时，全表扫描可能比走索引更省，这并不是固定阈值
附带因素为避免排序（ORDER BY ... LIMIT）而选了有序的索引，反而扫了很多行
条件无法估算函数、表达式、隐式转换导致无法用索引估行数

处理手段（由轻到重）

  1. ANALYZE TABLE 刷新统计；倾斜列建直方图。
  2. 改写 SQL，让条件可以用上索引，必要时补 / 调整索引（联合索引顺序、覆盖索引）。
  3. 给优化器「提示」：
    • 索引提示：USE INDEX / FORCE INDEX / IGNORE INDEX。
    • 优化器 Hint（5.7.7+）：SELECT /*+ INDEX(t idx_a) */ ...，另有 NO_INDEX、JOIN_ORDER、HASH_JOIN / NO_HASH_JOIN、MAX_EXECUTION_TIME(ms)（只对 SELECT）、SET_VAR(var=val)（仅对当前语句改变量）。
  4. 调整 optimizer_switch 里的开关（如 index_merge、mrr、hash_join），影响全局或会话的优化策略，需谨慎。

强制索引是「治标」：数据分布变化后可能反而成为问题，优先让统计和索引设计合理。

4.5 看优化器的「思考过程」：optimizer_trace

EXPLAIN 只给结果，想知道为什么选这个方案，用 trace：

SET optimizer_trace = 'enabled=on';
-- 执行要分析的语句
SELECT ... ;
SELECT trace FROM information_schema.OPTIMIZER_TRACE\G
SET optimizer_trace = 'enabled=off';

输出是 JSON，主要关注三个阶段：

阶段内容
join_preparation预处理、语法树改写的结果
join_optimization条件处理（condition_processing）、各表行数估计（rows_estimation）、每种候选访问方式的成本（considered_access_paths）、候选 join 顺序（considered_execution_plans）、最终选择
join_execution执行阶段信息，如排序（filesort_summary：用了多少个临时文件、排序算法）

trace 过长被截断时，调大 optimizer_trace_max_mem_size。

5. 执行器

5.1 取数模型

执行器按优化器给出的计划，通过 Handler API 向引擎要数据，再在 Server 层完成过滤、关联、排序、聚合、返回。

  • 无可用索引：反复调「读下一行」做全表扫描，每行在 Server 层判断 WHERE。
  • 有索引：调「按索引找到第一个满足条件的行」，再「读下一个」，直到条件不满足。
  • 条件能否在引擎层提前判断（索引条件下推 ICP），决定了有多少无效行被传回 Server 层（见第 7 节）。

5.2 8.0 的迭代器（Iterator）模型

8.0 逐步把执行器改造成 Volcano 迭代器模型：执行计划是一棵由迭代器组成的树，每个迭代器实现 Init() / Read()，上层不断向下层「拉」一行。典型迭代器：表扫描、索引扫描、Filter、Nested Loop Join、Hash Join、Sort、Aggregate、Limit……

好处：结构统一、便于实现 Hash Join 与 EXPLAIN ANALYZE。EXPLAIN FORMAT=TREE 直接展示这棵树：

-> Limit: 10 row(s)
    -> Sort: o.amount DESC, limit input to 10 row(s) per chunk
        -> Filter: (o.status = 1)
            -> Table scan on o

（示意，具体文字与数值随版本和环境而变。读法：最内层最先执行，数据自下向上流动。）

5.3 其他要点

  • 结果流式返回：边算边发（见第 0 章），LIMIT 满足后立即停止，不会继续扫描。
  • 慢日志的 rows_examined 大致是执行器调用引擎取行的次数。
  • 写操作（INSERT / UPDATE / DELETE）的执行器流程多了加锁、undo、redo、binlog，见事务、锁、日志章节。

6. 执行计划 EXPLAIN

交互实验 打开《一条 SELECT 的旅程》

走到优化器这一步，对照示例 EXPLAIN 的访问类型和索引字段。也可以阅读静态步骤。

6.1 四种用法

命令说明
EXPLAIN传统表格，只估算不执行
EXPLAIN FORMAT=JSON含成本（cost_info）、使用的索引列、附加条件等更详细信息
EXPLAIN FORMAT=TREE（8.0.16+）迭代器树，直观看到执行顺序和 join 方式
EXPLAIN ANALYZE（8.0.18+）真正执行语句并给出实际耗时、实际行数、循环次数，输出为 TREE 格式

另有 EXPLAIN FOR CONNECTION <id>，查看正在执行的会话的计划。

EXPLAIN ANALYZE 会真实执行语句，用于 UPDATE / DELETE 之类写语句要格外小心，先在测试环境或确认可回滚时使用。

6.2 传统格式各列

示例表：

CREATE TABLE t_order (
  id         BIGINT AUTO_INCREMENT PRIMARY KEY,
  user_id    INT NOT NULL,
  status     TINYINT NOT NULL,
  amount     DECIMAL(10,2) NOT NULL,
  created_at DATETIME NOT NULL,
  KEY idx_user_created (user_id, created_at),
  KEY idx_status (status)
) ENGINE=InnoDB;
列含义
id查询块序号。id 越大越先执行，id 相同自上而下执行（同一 id 内，上面的表是驱动表）
select_type查询块类型：SIMPLE（无子查询 / union）、PRIMARY、SUBQUERY、DEPENDENT SUBQUERY（相关子查询，每行外层都要跑一次，要警惕）、DERIVED（派生表）、UNION、UNION RESULT、MATERIALIZED
table访问的表（或派生表 <derivedN>、<subqueryN>）
partitions命中的分区
type访问类型，最重要的一列，见 6.3
possible_keys可能用到的索引
key实际选用的索引；NULL 表示没用索引
key_len用到的索引字节数，见 6.4
ref与索引比较的对象（常量 const、其他表的列）
rows估计需要检查的行数
filtered经表上过滤条件后，估计剩余行数百分比；rows × filtered% ≈ 传给下一个表的行数
Extra额外信息，见 6.5

6.3 type：访问类型（好 → 坏）

system > const > eq_ref > ref > fulltext > ref_or_null > index_merge > unique_subquery > index_subquery > range > index > ALL

type含义例子
system / const主键或唯一索引等值匹配常量，最多一行WHERE id = 100
eq_refjoin 时，被驱动表用主键或唯一非空索引等值匹配，每次最多一行JOIN b ON a.bid = b.id
ref非唯一索引（或唯一索引的前缀）等值匹配，可能多行WHERE user_id = 7
range索引范围扫描BETWEEN、>、<、IN、LIKE 'abc%'
index全索引扫描，遍历整棵索引树（比 ALL 好在索引通常更小、若覆盖则不回表）覆盖索引但无过滤条件
ALL全表扫描（聚簇索引全扫）无可用索引

日常目标：至少到 range，join 的被驱动表争取 ref / eq_ref。大表上看到 ALL 或 index 要警觉。

6.4 key_len：判断联合索引用到了几列

key_len 是实际使用的索引长度（字节），可反推用了联合索引的前几列。常见类型长度：

类型长度备注
INT4
BIGINT8
DATE3
DATETIME5无小数秒；有小数秒更长
TIMESTAMP4
CHAR(n)n × 字符集最大字节数utf8mb4 每字符 4 字节
VARCHAR(n)n × 字符集最大字节数 + 2
允许 NULL额外 +1

示例（idx_user_created (user_id INT NOT NULL, created_at DATETIME NOT NULL)）：

  • 只用到 user_id：key_len = 4
  • 两列都用到：key_len = 4 + 5 = 9

如果你以为联合索引的两列都用上了，key_len 却只有 4，说明第二列没有被用来定位，只能靠回表或下推过滤。

6.5 Extra：最需要读懂的一列

Extra含义好 / 坏
Using index覆盖索引：只读索引就能拿到所有需要的列，不回表好
Using index condition用了 ICP（索引条件下推）：部分 WHERE 在引擎层的索引上判断，减少回表好
Using whereServer 层对引擎返回的行做过滤中性，本身不代表差
Using index; Using where覆盖索引，且在 Server 层再过滤中性偏好
Using filesort需要额外排序，没能直接利用索引的有序性（不一定写磁盘）数据量大时要优化
Using temporary使用了内部临时表（GROUP BY、DISTINCT、UNION、派生表等）数据量大时要优化
Using join buffer (hash join) / (Block Nested Loop)被驱动表没有可用索引，用 join buffer 缓解通常说明缺索引
Using join buffer (Batched Key Access)使用 BKA视情况
Using MRR使用多范围读优化视情况
Using index for group-by利用索引完成分组，无需临时表好
Using index for skip scan（8.0.13+）跳跃扫描：联合索引缺少前导列等值条件时，对前导列的不同值逐个扫描有条件时有用
Using intersect(...) / Using union(...) / Using sort_union(...)index merge：对多个索引的结果做交集 / 并集往往说明缺少合适的联合索引
Backward index scan倒序扫描索引（ORDER BY ... DESC 可利用，8.0 另支持真正的降序索引）好
Select tables optimized away如 MIN / MAX / COUNT(*)（MyISAM）直接从索引或元数据得到好
Impossible WHERE条件恒假，不需要访问表提示逻辑可能有误

8.0 变化：GROUP BY 不再隐式排序。5.7 中 GROUP BY 常伴随 Using filesort；8.0 若需要有序结果，必须显式写 ORDER BY。

6.6 EXPLAIN ANALYZE 怎么读

示意输出（数值随环境而变）：

-> Filter: (o.status = 1)  (cost=10.5 rows=100) (actual time=0.040..2.310 rows=96 loops=1)
    -> Table scan on o  (cost=10.5 rows=1000) (actual time=0.030..1.900 rows=1000 loops=1)
字段含义
cost=… rows=…优化器估算的成本和行数
actual time=a..b首行返回耗时..全部返回耗时，单位毫秒，是每次循环的平均值
rows=实际返回行数（同样是每次循环的平均值）
loops=该节点被执行的次数，总行数 ≈ rows × loops，总耗时 ≈ 时间 × loops

最有价值的用法：比较估算 rows 与实际 rows。两者数量级差距大，说明统计信息失真（回到 4.3 的处理手段）；loops 很大的节点往往是被驱动表，是优化重点。

6.7 EXPLAIN 的局限

  • 不执行语句（ANALYZE 除外），rows、filtered 都是估算。
  • 不反映函数、触发器、存储过程的内部开销。
  • 不反映缓存状态：同一计划在数据已在 Buffer Pool 与全在磁盘上耗时相差巨大。
  • 它描述「怎么查」，不直接告诉你「是否真的慢」，要结合慢日志的实际耗时判断。

7. 常见执行方式

7.1 回表与覆盖索引

  • 回表：通过二级索引找到主键值，再回聚簇索引取完整行。每次回表可能是一次随机 IO。
  • 覆盖索引：查询所需列都在索引里，不回表，Extra 为 Using index。例：SELECT user_id, created_at FROM t_order WHERE user_id = 7，只需读 idx_user_created。
  • 避免回表的常见做法：把常用查询列加进联合索引；少用 SELECT *。

7.2 ICP：索引条件下推（Index Condition Pushdown）

  • 场景：联合索引里有些列无法用来定位范围（如 LIKE '%xx%'），但它们的值就在索引里。
  • 没有 ICP：引擎按能定位的条件取行并回表，Server 层再过滤。
  • 有 ICP：这些条件在引擎层先在索引上判断，不满足的不回表，减少回表次数。
  • 特点：仅适用于二级索引；聚簇索引上数据本来就在叶子节点，没有收益；覆盖索引也不需要。标志是 Using index condition；开关为 optimizer_switch 中的 index_condition_pushdown（默认 on）。

7.3 MRR：多范围读（Multi-Range Read）

  • 问题：二级索引范围扫描得到的主键值是乱序的，逐个回表是随机 IO。
  • 做法：先把一批主键值缓存并排序，再按主键顺序回表，把随机 IO 变成近似顺序 IO。
  • 标志 Using MRR。mrr_cost_based 默认 on，优化器按成本决定是否使用，因此经常不触发；想强制需 mrr=on 并关掉 mrr_cost_based，要先用测试验证收益。

7.4 Join 相关：BNL / Hash Join / BKA

算法要点
Index Nested Loop被驱动表有索引，驱动表每行去索引里查，最理想
Block Nested Loop（BNL）被驱动表无索引时，把驱动表的多行放进 join_buffer，一次扫描被驱动表就能匹配多行，减少扫描次数；join_buffer_size 默认 256KB。8.0.20 起被 Hash Join 取代
Hash Join（8.0.18+）对等值 join 且无索引的场景，用驱动表建哈希表，扫描被驱动表探测，Extra 为 Using join buffer (hash join)
BKA批量取驱动表的 join key，配合 MRR 去被驱动表批量查找，默认关闭（batched_key_access=off），需 mrr=on、mrr_cost_based=off

看到 Using join buffer 的第一反应：被驱动表的 join 列是否缺索引。

7.5 Filesort：额外排序

  • 无法利用索引有序性时，Server 层把需要排序的数据放进 sort_buffer（sort_buffer_size，默认 256KB），在内存里排；放不下就写临时文件分块排序再归并（外部排序）。
  • 「Filesort」名字有误导：它不一定落磁盘，只表示「不是靠索引直接得到有序」。判断是否落盘看 optimizer_trace 中 filesort_summary 的 number_of_tmp_files。
  • 优化方向：让 ORDER BY 的列顺序与索引一致（可以走索引直接有序）；LIMIT 场景下 MySQL 会用优先队列（堆）只维护前 N 条；单路 / 双路排序由 max_length_for_sort_data 影响。算法细节见查询优化章。

7.6 临时表：Using temporary

  • 触发：GROUP BY / DISTINCT 无法利用索引、UNION（去重）、派生表物化、某些 ORDER BY 与 GROUP BY 组合等。
  • 引擎：8.0 默认内存临时表用 TempTable 引擎（5.7 是 MEMORY）；内存超限后转为磁盘临时表（InnoDB）。5.7 中磁盘临时表是 MyISAM（可配置为 InnoDB）。
  • 监控：SHOW GLOBAL STATUS LIKE 'Created_tmp%'，Created_tmp_disk_tables 增长快说明大量临时表落盘。
  • 优化方向：给分组 / 去重字段建合适索引，减少参与分组的数据量。

8. 实战：读一个执行计划的步骤

  1. 看 type：是否 ALL / index；表很大时必须关注。
  2. 看 key 和 possible_keys：key 为 NULL 但 possible_keys 不为空，说明优化器嫌索引不划算；去查统计 / 数据分布。
  3. 看 key_len：联合索引实际用了几列。
  4. 看 rows 与 filtered：驱动表行数乘以后续表的行数，估算整体量级。
  5. 看 Extra：Using filesort、Using temporary、Using join buffer、Using index condition 等。
  6. 用 EXPLAIN ANALYZE 对比估算与实际，定位估算失真或循环过多的节点。
  7. 需要追问「为什么」时用 optimizer_trace。
  8. 修复后复测：先 ANALYZE TABLE，再看计划和实际耗时，不要只看 EXPLAIN。

常见红灯

现象可能原因
type=ALL，key=NULL无索引，或条件对索引列做了函数 / 隐式转换
rows 极大缺索引、索引选择性差
key_len 比预期短联合索引的后续列没用上（最左前缀被打断、范围条件之后的列无法用于定位）
Using filesort + 大 rows排序字段没索引，或 ORDER BY 与索引顺序不一致
DEPENDENT SUBQUERY相关子查询，每个外层行执行一次，考虑改写为 join
估算与实际行数差几个数量级统计过期或数据倾斜

10. 常见面试题

Q1：一条 SQL 在 Server 层经过哪几个阶段？ 解析（词法、语法）→ 预处理（名字解析、权限、语义检查）→ 优化（逻辑改写 + 基于成本选计划）→ 执行（执行器通过 Handler API 向引擎取数并处理）。

Q2：EXPLAIN 中 type 从好到坏怎么排？各举一例。 system / const（主键等值）> eq_ref（join 时主键等值）> ref（普通索引等值）> range（范围）> index（全索引扫描）> ALL（全表扫描）。

Q3：Using index、Using index condition、Using where 的区别？

  • Using index：覆盖索引，不回表。
  • Using index condition：ICP，部分条件在引擎层的索引上判断，减少回表，但仍然会回表。
  • Using where：Server 层对引擎返回的行再做过滤，只表示有过滤，不是性能问题的标志。

Q4：为什么优化器会选错索引？怎么办？ 统计信息不准、回表成本估算偏差、为避免排序而选了有序索引等。先 ANALYZE TABLE / 建直方图，再改写 SQL 或调整索引；无法解决时使用 FORCE INDEX 或优化器 Hint，并关注数据分布变化后的回归。

Q5：EXPLAIN 里的 rows 是怎么来的？准吗？ 来自索引统计（采样得到的基数）或 range 场景下的索引潜水，是估算值，可能有数量级偏差；用 EXPLAIN ANALYZE 对比实际行数。

Q6：怎么通过 key_len 判断联合索引用了几列？ 根据各列类型长度（含是否允许 NULL、字符集）累加。如 (INT NOT NULL, DATETIME NOT NULL)：只用第一列是 4，两列都用是 9。

Q7：预编译语句有什么作用？ SQL 只解析一次，减少解析开销；参数与语句分离，防 SQL 注入。但 MySQL 不缓存执行计划，每次执行仍会优化。

Q8：EXPLAIN ANALYZE 和 EXPLAIN 的区别？ 前者真正执行语句并给出实际耗时、行数、循环次数，可与估算对比；后者只估算。写语句使用要小心。

Q9：什么是回表？怎么减少？ 二级索引找到主键后回聚簇索引取完整行。用覆盖索引、减少 SELECT *、ICP、MRR 来减少或优化回表代价。

Q10：5.7 升级 8.0，SQL 层面有哪些坑？ 新保留字导致语法错误、GROUP BY 不再隐式排序、查询缓存移除、部分优化器行为变化导致执行计划改变（升级前后对比核心 SQL 的执行计划）。

11. 本章小结

  • 阶段：解析 → 预处理 → 优化 → 执行；每一步都有对应的典型错误和排查手段。
  • 优化器：基于成本，成败取决于统计信息；选错索引先修统计，再改写，最后用 Hint。
  • 执行器：8.0 起是迭代器模型，EXPLAIN FORMAT=TREE / ANALYZE 直接展示。
  • 读计划抓四点：type、key / key_len、rows / filtered、Extra；ANALYZE 用来比较估算与实际。
  • 常见执行方式：覆盖索引、回表、ICP、MRR、BNL / Hash Join / BKA、Filesort、临时表。
