适用：MySQL 8.0.x（与 5.7 的差异单独标注）。知识地图见 MySQL 知识总览。

目标：看完能画出 MySQL 的分层架构，说清一条 SELECT / UPDATE 从进来到出去经过了哪些组件，以及每个组件的职责边界。

1. 一张图看全局

三句话记忆：

  • Server 层管理客户端连接与认证，并负责解析 SQL、选择执行计划和协调执行。
  • 引擎层：管「数据怎么存、怎么取、事务和锁怎么做」，可插拔，通过统一的 Handler 接口和 Server 层对话。
  • 文件层：最终落盘的东西。

2. 各层职责

2.1 Server 层的连接管理

要点说明
通信协议TCP / Unix Socket；客户端与服务端是半双工，一次只能一方发
认证校验账号、host、密码；8.0 默认插件 caching_sha2_password，5.7 是 mysql_native_password
权限生效时机表 / 列级权限的变更在下一条语句生效；库级权限在下次 USE db 生效；全局权限和密码的变更只对新连接生效，已有连接不受影响
线程模型社区版默认一连接一线程，线程可缓存复用（thread_cache_size）；线程池（thread pool）是企业版 / Percona / MariaDB 的能力
连接数max_connections（默认 151），超出报 Too many connections；管理员账号可额外多 1 个连接
空闲超时wait_timeout（默认 28800 秒），空闲连接超时被服务端断开

长连接的坑：连接过程中临时使用的内存只有在连接断开时才释放，长连接累积后内存可能涨得很高，表现为 OOM 被系统杀。处理方式：

  • 定期断开长连接，或在大查询后由应用主动重置。
  • 5.7+ 可以调用 mysql_reset_connection 重新初始化连接资源，不用重连也不用重新鉴权。

2.2 Server 层的 SQL 处理

执行顺序：解析 → 预处理 → 优化 → 执行。

组件职责产出
解析器词法分析识别关键字、表名、列名；语法分析判断是否符合 MySQL 语法语法树（AST），语法错误在这里报 You have an error in your SQL syntax
预处理名字解析：表、列是否存在，* 展开，视图展开；表级 / 列级权限检查带有元数据信息的语法树
优化器基于成本（CBO）选择执行计划：用哪个索引、Join 顺序、是否用临时表 / filesort执行计划
执行器按计划循环调用引擎接口取数 / 写数，做过滤、聚合、排序，把结果返回客户端结果集

补充：

  • 8.0 之前 Server 层还有查询缓存，8.0 已移除。原因：只要表有任何更新，该表的所有缓存全部失效，命中率低，且维护缓存有锁竞争。不要再在 8.0 上找 query_cache_*。
  • 执行器的取数模式（无索引 / 有索引）：
    • 无索引：调用引擎「读第一行」→ 判断条件 → 「读下一行」…直到读完。
    • 有索引：调用引擎「按索引找到第一个满足条件的行」→ 「读下一个」…直到不满足。
  • 慢日志里的 rows_examined 大致对应执行器调用引擎取行的次数，但不一定等于引擎实际扫描的行数（如覆盖索引、索引下推场景会有差异）。
  • 内置能力在 Server 层：函数、视图、存储过程 / 函数、触发器、事件、权限体系、binlog。

2.3 存储引擎层

  • 引擎是表级别可选的（建表 ENGINE=...），Server 层通过 Handler API 调用，例如读下一行、按索引读、写行、更新行、删除行。
  • 8.0 的 SHOW ENGINES 可以看到当前支持的引擎。
引擎事务锁粒度特点 / 现状
InnoDB支持行锁5.5 起成为默认引擎，支持 MVCC、外键、崩溃恢复，生产唯一首选
MyISAM不支持表锁不崩溃安全；8.0 起系统表也迁到了 InnoDB，基本只剩历史遗留
Memory不支持表锁数据在内存、重启丢失，常见用途是内部临时表
其他CSV、Archive、Blackhole、Federated、NDB（MySQL Cluster）等，特定场景使用

2.4 文件层（8.0 datadir 里的主要文件）

文件说明
*.ibd独立表空间（innodb_file_per_table=ON，默认），一个表一个文件，存数据和索引
ibdata1系统表空间：Change Buffer、doublewrite（8.0.20 之前）等
mysql.ibd8.0 数据字典，表结构元数据存在 InnoDB 里，不再有 .frm
undo_001 / undo_002undo 表空间（8.0 默认两个，独立于 ibdata1）
#innodb_redo/redo 日志目录（8.0.30+）；更早是 ib_logfile0 / ib_logfile1
binlog.000001 + binlog.index二进制日志及其索引（8.0 默认开启）
ibtmp1 / #innodb_temp/临时表空间
错误日志、慢日志、通用日志文本日志，各自参数控制开关

查看位置：SHOW VARIABLES LIKE 'datadir';

3. 谁在 Server 层，谁在引擎层

这是理解 MySQL 的关键分界线，面试很爱问「某某功能属于哪一层」。

能力所在层备注
连接 / 认证 / 权限Server
解析 / 优化 / 执行Server
元数据锁（MDL）Server保护表结构，DDL 与 DML 互斥的来源
binlogServer所有引擎都有，用于归档、复制、PITR
redo log / undo logInnoDBInnoDB 独有，用于崩溃恢复和回滚 / MVCC
事务、MVCCInnoDB引擎自己实现，MyISAM 没有
行锁、间隙锁InnoDB
Buffer Pool、数据页、索引 B+TreeInnoDB

推论：binlog 和 redo log 分属两层，所以才需要「两阶段提交」来保证它们一致，详见后续「日志体系」章节。

4. 一条 SELECT 的旅程

以 SELECT * FROM t WHERE k = 5; 为例：

  1. 建立连接时，Server 层完成握手、认证并分配线程。
  2. 解析：词法、语法分析生成 AST。
  3. 预处理：确认表 t、列 k 存在，展开 *，检查权限；同时在表上加 MDL 读锁。
  4. 优化：评估走 k 的索引还是全表扫描，选成本最低的计划。
  5. 执行：执行器调用 InnoDB 接口，通过索引树找到 k=5 的记录；若是二级索引且需要其他列，还要回表到聚簇索引；数据页优先从 Buffer Pool 读，没有才读磁盘。
  6. 返回结果：边读边发，不是把结果全部算完再发。数据先写入连接的 net_buffer（默认 16KB），写满后再写到 socket 发送缓冲区，客户端读走后继续。因此大结果集不会撑爆服务端内存，但客户端读得慢会让线程停在 Sending to client 状态。

观察：SHOW PROCESSLIST; 或 performance_schema.threads 看线程当前状态。

7. 常见面试题

Q1：一条 SQL 在 MySQL 里是怎么执行的？ Server 层建立连接并完成认证，随后解析、预处理、优化 SQL，再由执行器调用引擎取数并逐步返回给客户端。更新操作还会涉及 undo、redo、binlog 和两阶段提交。

Q2：为什么 MySQL 分 Server 层和引擎层？ Server 层通过统一接口调用可插拔的存储引擎，不同引擎可以共用 Server 层的连接管理和 SQL 处理流程。跨层功能需要协调，例如两阶段提交保证 binlog 和 InnoDB redo log 的一致性。

Q3：8.0 为什么删掉查询缓存？ 任何表更新都会使该表的全部缓存失效，在写多读少或更新频繁的场景命中率极低，并且缓存的维护带来锁竞争。缓存应放在应用层（Redis 等）自行控制。

Q4：连接数过多怎么排查和处理？ 看 SHOW PROCESSLIST 里都是什么状态（大量 Sleep 是连接泄漏或连接池配置过大，大量 Query 是慢 SQL 或锁等待）；处理：优化慢 SQL、限制 / 回收空闲连接（wait_timeout）、使用连接池或中间件；max_connections 调大只是缓解，不要当根治手段。

Q5：MySQL 长连接内存为什么会越涨越高？怎么办？ 连接内的临时资源在断开前不会释放。定期断开长连接，或 5.7+ 用 mysql_reset_connection 重置。

Q6：binlog 和 redo log 的区别？

  • 层级：binlog 在 Server 层，所有引擎可用；redo log 是 InnoDB 独有。
  • 内容：binlog 是逻辑日志（记录语句或行变化）；redo log 是物理日志（记录数据页的修改）。
  • 写法：binlog 追加写；redo log 循环写。
  • 用途：binlog 用于复制和恢复到任意时间点；redo log 用于崩溃恢复。

8. 本章小结

  • 客户端通过 Server 层建立会话并提交 SQL，Server 层通过 Handler API 调用存储引擎。
  • 分界线：binlog、MDL、优化器在 Server；redo、undo、MVCC、行锁在 InnoDB。
  • 结果返回是流式的，更新则多出日志与锁的一整套机制。
  • 8.0 去掉了查询缓存，数据字典进了 InnoDB。
